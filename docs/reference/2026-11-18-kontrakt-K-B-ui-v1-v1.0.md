# 1. Что такое К-Б

К-Б — граница между **экраном** (браузер, MiniApp MAX, модуль ИН-ВМ в приложении банка) и **сервером приложения**. Сервер приложения — это тот же процесс, что сейчас отдаёт пульт и монитор (`src/demo/server.ts`). Он держит ядро агента и ходит в ПАО.

```
экран  ──/ui/v1──▶  сервер приложения  ──▶  ядро агента (Purchase)  ──ПАО 1.4.0──▶  Платформа
                                        └─▶  витрины продавцов (заказ, живая проверка)
```

Экран не ходит на Платформу и к продавцам. У экрана нет ключа агента, `kid`, криптограммы реквизита и номера карты (инвариант 1). Экран — недоверенная среда (С-12, С-31, С-32).

# 2. Три поправки к передаче 18.11 (по коду)

1. **INTENT подписывает человек в банке, а не ключ агента.** По ПАО новый мандат имеет статус `PENDING_SIGNATURE`, и подпись ставит принципал в банке: подпись банка над `Mandate.hash` (РП36). Ключ агента (`kid`) подписывает только обращения агента к ПАО. Поэтому метод `POST /ui/v1/intent/sign` из передачи **не подписывает**: он отправляет поручение и возвращает маршрут подписи в банк. Новое имя метода — `POST /ui/v1/intent`. На стенде маршрут ведёт на экран мандатов банка (UI-К2, открывается ссылкой, Р-1313). В ИН-ВМ подпись делает модуль банка внутри приложения банка.
2. **CART банк не подписывает.** По РП35 мандат CART сразу получает статус `ACTIVE`: в ядре `CART_PENDING → CART_ACTIVE` идут подряд. Согласие человека на корзину — это жест на нашем экране (У5), привязанный к хэшу показанного (правило 1) и провенансу П26. Новое имя метода — `POST /ui/v1/cart`.
3. **Живая проверка идёт до CART и ещё раз перед заказом.** Ядро проверяет цены непосредственно перед запросом CART (Р43 п. 1) и снова перед заказом (Р32 п. 3–4). Поэтому `POST /ui/v1/check` (У4) — это предварительный показ человеку. Цена, которая уйдёт в CART, берётся из повторной проверки внутри `POST /ui/v1/cart`. Если она изменилась, человек видит новую цену и подтверждает её заново (новый выбор, Т6).

Кроме того, в перечне передачи нет пяти методов, без которых экраны У1–У10 не собираются. Они добавлены в § 5 и помечены: состояние покупки, история, спор, обучение, подпись принципов.

# 3. Общие правила контракта

## Правило 1. Хэш показанного

Сервер отдаёт каждую карточку, которую человек подтверждает (поручение, корзина, оплата, принципы), вместе с объектом `view`:

```json
"view": { "view_id": "vw_…", "text_version": "u1-card@1.0", "hash": "sha256:…" }
```

`hash` — SHA-256 канонического JSON карточки, то есть ровно того, что экран показывает человеку: поля и тексты, без оформления. Экран отправляет обратно `shown_hash`, равный `view.hash` показанной карточки. Сервер пересчитывает хэш по своей копии `view_id`. Если хэш не совпал или карточка устарела, сервер отвечает **409 `SHOWN_STALE`** и выдаёт новую карточку, а обращения к ПАО нет. Так закрывается С-07 «подписывают невиденную корзину».

Тем же телом уходит провенанс нажатия П26:

```json
"press": { "at": "2026-11-18T12:04:31.120Z", "device": "mobile", "text_version": "u1-card@1.0", "gesture": "swipe" }
```

`at` — время по часам устройства. Сервер добавляет своё время получения и не заменяет им время устройства. `device` принимает значения `mobile` | `web` | `max` | `bank_module`. `gesture` — `swipe` для подписи жестом (правка 5 канвы) или `tap`. Сервер записывает провенанс в журнал покупки.

## Правило 2. Идемпотентность каждого POST

Каждый POST несёт заголовок `Idempotency-Key`: UUID v4, его генерирует экран при первом нажатии. При повторе (двойное «Подтвердить» — С-09, обрыв связи при оплате — С-18) экран шлёт тот же ключ. Сервер отвечает так же, как ПАО:

- тот же ключ и то же тело — тот же ответ, второго действия нет;
- тот же ключ и другое тело — **409 `IDEMPOTENCY_CONFLICT`**;
- без ключа — **400 `IDEMPOTENCY_REQUIRED`**.

Ключ экрана и ключ обращения ядра к ПАО разные. Сервер выводит ключ ядра из ключа экрана детерминированно, поэтому повтор экрана — это и повтор к ПАО тем же ключом.

## Правило 3. Экран ничего не считает

Экран не взвешивает принципы, не ранжирует варианты, не решает, что укладывается в пределы, и не складывает суммы. Сервер отдаёт готовыми: суммы, итог, строку «что не списано», тексты «почему так», причины отсева, доступность кнопок вместе с объяснением недоступного. Иначе правило «вес исполнения не ниже веса цены» (ст. 19) жило бы в двух местах.

## Правило 4. Поток событий — только сигнал (новое)

До ПАО 1.5.0 события Платформы не подписаны (инвариант 9, SEC-1 ч. 3). Поэтому `GET /ui/v1/feed` говорит только, что **что-то изменилось**. Получив событие, экран перечитывает состояние через `GET /ui/v1/purchase/{id}` или `GET /ui/v1/order/{id}` и показывает только прочитанное. «Оплачено», «Отклонено» и «Остановлено» по одному событию экран не показывает.

## Деньги, время, тексты

- **Деньги** — всегда пара `{ "amount": 36800, "currency": "RUB" }`: целое число в минимальных единицах и код ISO 4217 (правило плана «Россия» № 2). В ПАО 1.4.0 у операции нет валюты, её подставляет сервер из CART покупки. Экран всегда получает пару.
- **Время** — UTC в формате ISO 8601. Пояс человека экран применяет только для показа.
- **Тексты** — сервер отдаёт код и готовый текст на языке запроса (`?lang=ru|en`, как у монитора). Бренд берётся из конфигурации приложения (правило плана «Россия» № 3). Тексты О11 не утверждены: в v1.0 это примеры в пользовательском регистре.

## Ошибки

Тело ошибки одно для всех методов:

```json
{ "error": { "code": "LIMIT_EXCEEDED", "retry": "after_human", "text": "Сумма больше остатка поручения: 632 ₽", "view": null } }
```

`code` — код из перечня отказов ядра (`FailureCode`, `src/shared/domain.ts`) или код `/ui` из § 6. `retry` — класс повтора ядра: `never` | `after_fix` | `same_key` | `after_human`. Класс `new_key` экрану не отдаётся: это смена ключа подписи агента, и делает её сервер. `text` предназначен для человека. `view` заполнен, когда сервер выдаёт новую карточку (например, при `SHOWN_STALE`).

## Авторизация

Авторизация — параметр контракта, второго контракта нет.

- Веб и MAX: сессия приложения, cookie same-origin. Под CSP `'self'` это не меняется.
- ИН-ВМ: `Authorization: Bearer <токен банка>`. Происхождение токена и проверку определяет договор с банком. На стенде токен выдаёт банк стенда.

## Версии

Путь `/ui/v1` и ПАО `/pao/v1` меняются независимо. Совместимое расширение — новые необязательные поля. Несовместимое — только `/ui/v2`.

# 4. Состояние покупки — одно на все экраны

Экран узнаёт, где он, только из `state`, а `state` — это состояние машины ядра (`PURCHASE_STATES`):

| `state` ядра | Шаг экрана | Что видит человек |
|---|---|---|
| `NEW` | У1 | карточка поручения |
| `INTENT_PENDING` | У2 | «Подпишите поручение в банке», ссылка или модуль банка |
| `INTENT_ACTIVE` | У2 → У3 | поручение подписано, идёт поиск |
| `OFFERS` | У3 | варианты, «почему так», отсев |
| `CART_PENDING`, `CART_ACTIVE` | У4–У5 | живая проверка, корзина |
| `ORDERED` | У6 | оплата |
| `CONFIRMING` | У6 | «Подтвердите покупку на странице УПК или в приложении банка» |
| `AUTHORIZING` | У6 | «Идёт оплата» |
| `SETTLING` | У7 | «Оплачено, ждём итога расчёта» |
| `DONE` | У7 | итог и запись об исполнении |
| `STOPPED` | У7 | остановлено: код, текст, что дальше |

Сервер отдаёт `state` вместе с полем `step` (`U1`…`U7`), чтобы экран не держал таблицу у себя (правило 3).

# 5. Методы

Все тела — JSON, кроме потока событий. Поля, помеченные `?`, необязательны.

## 5.1 `POST /ui/v1/intent/draft` — фраза → карточка поручения (У1)

```json
// запрос
{ "phrase": "хлеб на выходные, до 1000 ₽, один раз" }
// ответ 200
{
  "draft_id": "drf_…",
  "card": {
    "subject": "хлеб",
    "limit": { "amount": 100000, "currency": "RUB" },
    "valid_to": "2026-11-25T12:00:00Z",
    "merchants": { "count": 7, "labels": ["Масса Мадре (MER-…)"] },
    "confirmation_mode": "IMMEDIATE",
    "lines": [ { "code": "LIMIT", "text": "До 1 000 ₽ за всё поручение" } ]
  },
  "questions": [],
  "actions": { "submit": { "enabled": true, "label": "Сохранить поручение", "why_disabled": null } },
  "view": { "view_id": "vw_…", "text_version": "u1-card@1.0", "hash": "sha256:…" }
}
```

Поля `card` — это `MandateDraft` ядра в пользовательском регистре. `questions` — уточнения, если фраза неполная.

**На стенде до ВР-5** «понимание запроса» карточка собирается из шаблона (`IntentCard`, `scenarios.ts`), а фраза только записывается в журнал. С ВР-5 карточку собирает решатель.

## 5.2 `POST /ui/v1/intent` — отправить поручение на подпись (У2)

Метод заменяет `intent/sign` из передачи (§ 2 п. 1).

```json
// запрос
{ "draft_id": "drf_…", "shown_hash": "sha256:…", "press": { … } }
// ответ 202
{
  "purchase_id": "pur_…",
  "state": "INTENT_PENDING", "step": "U2",
  "mandate": { "id": "mdt_…", "kind": "INTENT", "status": "PENDING_SIGNATURE" },
  "sign": { "where": "BANK", "link": "https://…/bank/mandates/mdt_…", "text": "Подпишите поручение в приложении банка" }
}
```

Сервер вызывает `Purchase.intent(draft)`, а ядро — `POST /pao/v1/mandates`. `sign.link` на стенде указывает на экран мандатов банка. В ИН-ВМ `sign.where` равен `BANK_MODULE`, а `link` равен `null`. Подписанный INTENT приходит сигналом в потоке, статус перечитывается по правилу 4. Порядок отзыва `revocation_order` задаёт Платформа (РП37), экран его только показывает. Поле приходит в `GET /ui/v1/purchase/{id}` после записи мандата.

## 5.3 `GET /ui/v1/purchase/{purchase_id}` — состояние покупки (добавлено)

```json
{
  "purchase_id": "pur_…", "state": "OFFERS", "step": "U3",
  "intent": { "id": "mdt_…", "status": "ACTIVE", "amount_left": { "amount": 100000, "currency": "RUB" },
              "valid_to": "…", "as_of": "…", "revocation_order": "…" },
  "done_line": { "done": "Поручение подписано", "not_spent": "Не списано: 1 000 ₽" },
  "stops": [],
  "actions": { "stop": { "enabled": true, "label": "Стоп", "why_disabled": null } }
}
```

`amount_left`, `valid_to` и `as_of` — исход `GET /pao/v1/mandates/{id}/verify`, остаток берётся только оттуда. `done_line` — строка «что уже сделано и что не списано» (правка 2 канвы), её собирает сервер. `stops` — вердикты по остановке П28 (§ 5.9).

## 5.4 `GET /ui/v1/offers?purchase_id=` — варианты, «почему так», отсев (У3)

```json
{
  "main": { "offer_id": "ofr_…", "shop": "Масса Мадре", "merchant_id": "MER-…", "sku": "…",
            "title": "Хлеб на закваске, 600 г", "price": { "amount": 36800, "currency": "RUB" },
            "zone": "CONTOUR", "seller_confirmed": true, "a5": [] },
  "why": [
    { "line": "PRICE", "text": "Дешевле двух других на 40–60 ₽", "source": "витрина продавца", "checked_at": "…", "confirmed": true },
    { "line": "STOCK", "text": "В наличии", "source": "витрина продавца", "checked_at": "…", "confirmed": true },
    { "line": "PRINCIPLES", "text": "Соответствует: местный производитель", "source": "ваши принципы", "checked_at": "…", "confirmed": true }
  ],
  "alternatives": [ { "offer_id": "…", "…": "как main", "compare_with_main": [ { "text": "+40 ₽, доставка завтра" } ] } ],
  "market": [ { "offer_id": "…", "zone": "MARKET", "link": "https://…", "disclosure_text": "Без гарантий покупки: только ссылка" } ],
  "filtered_out": { "count": 3, "items": [ { "shop": "…", "reason_code": "…", "text": "Вне ваших продавцов" } ] },
  "unavailable": [ { "shop": "…", "text": "Продавец недоступен" } ],
  "disclosure": { "contour": "…", "market": "…" }
}
```

Это `OfferZones` ядра (зоны `contour` и `market`, `unavailable`, коды пояснения `ZONE_CONTOUR` и `ZONE_MARKET`) плюс тексты сервера.

- `seller_confirmed: false` — пометка «сведения без подтверждения продавца» (белый каталог), видимая, а не мягкой формулировкой.
- `a5` — сигналы противоречивых сведений продавца (Р32): экран показывает их и собирает решение человека (`decision` в § 5.6).
- По зоне `MARKET` покупки нет, человеку даётся только ссылка (инвариант 10 ядра).
- `compare_with_main` — попарное «сравнить с главным». Таблица по позициям — только в вебе (ИН-ВЕБ).

## 5.5 `POST /ui/v1/check` — живая проверка у продавца (У4)

```json
// запрос
{ "purchase_id": "pur_…", "merchant_id": "MER-…", "lines": [ { "sku": "…", "qty": 1 } ] }
// ответ 200
{
  "ok": true,
  "lines": [ { "sku": "…", "qty": 1, "price": { "amount": 36800, "currency": "RUB" }, "fact": "OK", "text": "Цена и наличие подтверждены" } ],
  "checked_at": "…",
  "next": null
}
```

При `ok: false` `fact` — код живой проверки ядра (`LiveFactCode`), а `next` — следующий шаг словами: «к вариантам», «новый выбор». Это **предварительный показ**: окончательная проверка повторяется внутри `POST /ui/v1/cart` (§ 2 п. 3).

## 5.6 `POST /ui/v1/cart` — согласие на корзину (У5)

Метод заменяет `cart/sign` из передачи (§ 2 п. 2).

```json
// запрос
{ "purchase_id": "pur_…", "merchant_id": "MER-…",
  "lines": [ { "sku": "…", "qty": 1, "decision": null } ],
  "shown_hash": "sha256:…", "press": { … } }
// ответ 200
{
  "state": "ORDERED", "step": "U6",
  "cart": {
    "lines": [ { "title": "…", "qty": 1, "price": { "amount": 36800, "currency": "RUB" } } ],
    "goods_total": { "amount": 36800, "currency": "RUB" },
    "agent_fee": { "amount": 1, "currency": "RUB" },
    "agent_fee_text": "Цена агента — 1 копейка"
  },
  "mandate": { "id": "mdt_…", "kind": "CART", "status": "ACTIVE" },
  "order": { "order_id": "…" },
  "actions": { "pay": { "enabled": true, "label": "Купить за 368 ₽", "why_disabled": null } },
  "view": { … }
}
```

Сервер выполняет `Purchase.cart(choice)` (с `keyTermsShown: true` по факту показа) и затем `Purchase.placeOrder()`.

- Сумма заказа у продавца должна совпасть с CART (Т6). Если не совпала — 409 `ORDER_TOTAL_MISMATCH` и возврат к вариантам.
- `agent_fee` — отдельная строка и в корзине, и в итоге, в общую сумму не прячется. Где цена агента списывается и кем, в коде пока нет: это открытый вопрос монетизации (передача, «Прочее открытое»). До его решения поле показывается, но в сумме CART не участвует.
- `decision` — решение человека по сигналам A5 позиции. Без него при сигналах — 409 `A5_NEEDS_HUMAN` (`CartRefused` ядра).
- Изменилась цена при повторной проверке — 409 `PRICE_CHANGED` с новой карточкой в `error.view`.

## 5.7 `POST /ui/v1/payment` — оплата (У6)

```json
// запрос
{ "purchase_id": "pur_…", "mode": "BANK", "shown_hash": "sha256:…", "press": { … } }
// ответ 202
{
  "state": "AUTHORIZING", "step": "U6",
  "confirmation": null
}
// или, если сумма выше порога подтверждения банка
{
  "state": "CONFIRMING", "step": "U6",
  "confirmation": { "where": "UPK", "link": "https://…/upk/cnf_…", "expires_at": "…",
                    "text": "Подтвердите покупку на странице банка" }
}
```

- `mode: "BANK"` (М1) — `Purchase.authorize()`: реквизит через `POST /pao/v1/credentials`, продавцу уходит пакет, авторизацию ведёт продавец (РП2). Подтверждение выше порога `confirm_above_kop` создаёт ADP (РП50, РП51), человек подтверждает на странице УПК или в приложении эмитента (инвариант 7). Экран только открывает ссылку и ждёт.
- `mode: "MERCHANT_LINK"` | `"MERCHANT_QR"` (М2): оплата продавцу по ссылке или QR. **На стенде не работает** — 409 `NOT_ON_STAND`, текст «Оплата продавцу появится после решения вопроса стыка № 2», кнопка неактивна с объяснением. Держится вопросами стыка № 2 (оплата по ссылке на Платформе) и № 4 (оплата внутри MiniApp MAX).

## 5.8 `GET /ui/v1/order/{purchase_id}` — итог (У7)

```json
{
  "state": "DONE", "step": "U7",
  "operation": { "status": "SETTLED", "amount": { "amount": 36800, "currency": "RUB" }, "decline_text": null },
  "fulfilment": { "final": { "amount": 36800, "currency": "RUB" }, "scope_check": "WITHIN_LIMITS",
                  "scope_text": "В пределах поручения", "spent_position": { "amount": 36800, "currency": "RUB" }, "at": "…" },
  "source": { "text": "Запись об исполнении Платформы", "checked_at": "…" },
  "done_line": { "done": "Куплено", "not_spent": "Не списано: 632 ₽" },
  "refund": null,
  "stops": [],
  "agent_fee": { "amount": { "amount": 1, "currency": "RUB" }, "text": "Цена агента — 1 копейка (на стенде не списывается, § 8 п. 2)" },
  "act": { "id": "act_…", "card_url": "/ui/v1/act/act_…?view=card" }
}
```

`fulfilment` — запись об исполнении Платформы (`Fulfilment` ядра). `spent_position` экран не пересчитывает (инвариант 6 ядра). `scope_check` вне перечня приходит как `{ "other": "…" }`, текст «значение Платформы не опознано», без догадки.

`refund` после возврата:

```json
{ "status": "REFUNDED", "text": "Деньги вернулись. Лимит поручения не восстановлен" }
```

Бюджет при возврате не восстанавливается (РП71 п. 6, PS-23 ч. 2 — до пилота).

## 5.9 `GET /ui/v1/feed` — поток событий (SSE)

```
event: purchase
data: {"event_id":"…","purchase_id":"pur_…","kind":"STATE","at":"…"}
```

`kind` принимает значения `STATE` | `STOP` | `VERDICT` | `MANDATE` | `CONFIRMATION`. Только сигнал (правило 4): после события экран перечитывает § 5.3 или § 5.8. Доставка «не менее одного раза», повтор отбрасывается по `event_id`.

**Вердикт по остановке П28** приходит в `stops` (§ 5.3, § 5.8):

```json
{ "class": "BUS", "binding": "EXACT", "code": "…", "text": "…", "at": "…" }
{ "class": "STAND_LOG", "binding": "INEXACT", "code": "…", "text": "Привязка к покупке неточная", "at": "…" }
```

Экран рисует `BUS` сплошной рамкой, `STAND_LOG` — пунктиром с пометкой. Разница читается без цвета. П28 — рекомендация чата: поля `class` и `binding` действуют после «да» владельца по П28.

## 5.10 `POST /ui/v1/revoke` — отзыв поручения (У8)

```json
// запрос
{ "purchase_id": "pur_…", "press": { … } }
// ответ 202
{ "revoke": { "where": "BANK", "link": "https://…/bank/mandates/mdt_…", "order_text": "Порядок отзыва: …" },
  "agent": { "relinquished": true }, "state": "STOPPED" }
```

**Отзыв клиентом идёт через банк, не через ПАО** (РП38). Метод возвращает маршрут в банк и текст порядка отзыва (`revocation_order`). Агент со своей стороны отказывается от полномочий через `POST /pao/v1/mandates/{id}/relinquish` и останавливает покупку. Отказ от INTENT отзывает и его CART (РП35). Авторизованное до отзыва исполняется (инвариант 8 Платформы), и экран говорит об этом словами.

## 5.11 `GET /ui/v1/purchases` — история и повтор (У8, добавлено)

```json
{ "items": [ { "purchase_id": "…", "title": "Хлеб на выходные", "state": "DONE", "total": { … }, "at": "…",
              "actions": { "repeat": { "enabled": true, "label": "Повторить" } } } ],
  "next": null }
```

Повтор — это новая покупка с новой карточкой поручения, не копия старой подписи.

## 5.12 `POST /ui/v1/dispute` — спор (У9, добавлено)

```json
// запрос
{ "purchase_id": "pur_…", "reason": "NOT_DELIVERED", "press": { … } }
// ответ 202
{ "dispute": { "id": "…", "route": "IN_SCOPE", "route_text": "В пределах поручения — вопрос к магазину",
               "evidence_attached": true, "decision": "PENDING" } }
```

`reason` — из перечня ядра: `NOT_AUTHORIZED` | `QUALITY` | `NOT_DELIVERED`. Маршрут взят из модели: вне поручения «деньги возвращены», в пределах поручения «вопрос к магазину». Выписка из акта прикладывается сама (`GET /pao/v1/mandates/{id}/evidence`). ПАО требует `principal_ack` из банка, поэтому при необходимости ответ содержит ссылку в банк. **На стенде не работает до PS-22** — 409 `NOT_ON_STAND`.

## 5.13 `GET /ui/v1/act/{id}?view=card|full` — акт ACC-1

`view=card` — карточка-итог на мобильном: три числа и `full_link` («открыть целиком — в вебе»). `view=full` — все строки акта, только для ИН-ВЕБ. **Какие три числа**, определяет владелец. Предложение: «проверено», «нарушено», «не проверено» (сейчас проверяется 21 правило из 89).

## 5.14 `GET /ui/v1/principles` и `POST /ui/v1/principles` — принципы (П5)

```json
// GET → 200
{ "items": [ { "id": "…", "text": "Местный производитель", "rank": 1 } ],
  "signed": { "at": "…", "version": "…" } | null,
  "view": { … } }
// POST
{ "order": ["id1","id2","id3"], "shown_hash": "sha256:…", "press": { … } }
```

Экрану приходит только порядок важности (`rank`). Веса остаются в системном регистре и в ответ не попадают (правка 6 канвы). `POST` зависит от **П-К1 «принципы как подписываемый объект»** (база, 19.11): до П-К1 он отвечает 409 `NOT_ON_STAND`.

## 5.15 `GET /ui/v1/limits` — пределы и оплата (П6, он же ИН-ВМ)

```json
{
  "per_purchase": { "amount": 500000, "currency": "RUB" },
  "per_month": { "amount": 3000000, "currency": "RUB" },
  "confirm_above": { "amount": 300000, "currency": "RUB" },
  "signature_level": "K7",
  "funding": [ { "ref": "fnd_…", "label": "Карта банка" } ]
}
```

- `confirm_above` — порог `confirm_above_kop` из параметров стенда. Значение в примере условное, его даёт сервер.
- `funding.label` — текст банка. Номера карты и его частей в контракте нет (инвариант 1). Показывать ли последние цифры, решает банк, текстом метки.
- `signature_level` — уровень подписи из П4 канвы (K6/K7/K8). Его связь с уровнями `SignatureLevel` ядра (`simple` | `qualified` | `gov_id`) — открытый вопрос § 8.

## 5.16 `GET /ui/v1/learn` и `POST /ui/v1/learn/{id}` — обучение (У10, добавлено)

```json
// GET → 200
{ "question": { "id": "lrn_…", "text": "В прошлый раз вы выбрали дороже, но ближе. Учитывать близость выше цены?" } | null }
// POST
{ "answer": "ACCEPT" | "DECLINE", "press": { … } }
```

Один вопрос за раз. Принять или отклонить. **Пределов обучение не трогает никогда**: сервер отклоняет любое изменение пределов через этот метод.

# 6. Коды `/ui` сверх кодов ядра

| Код | HTTP | Когда |
|---|---|---|
| `SHOWN_STALE` | 409 | хэш показанного не совпал или карточка устарела; новая карточка в `error.view` |
| `PRICE_CHANGED` | 409 | цена изменилась при проверке перед CART |
| `ORDER_TOTAL_MISMATCH` | 409 | сумма заказа у продавца ≠ CART |
| `A5_NEEDS_HUMAN` | 409 | у позиции сигналы A5 без решения человека |
| `NOT_ON_STAND` | 409 | метод в контракте есть, на стенде его основы нет (М2, спор, принципы) |
| `IDEMPOTENCY_REQUIRED` | 400 | нет `Idempotency-Key` у POST |
| `IDEMPOTENCY_CONFLICT` | 409 | тот же ключ, другое тело |
| `PURCHASE_NOT_FOUND` | 404 | чужая, неизвестная или не по форме покупка — один ответ |
| `STEP_NOT_ALLOWED` | 409 | метод не на своём шаге (`PurchaseTransitionForbidden` ядра) |

Остальные коды — коды ядра (`FailureCode`) как есть, с классом повтора.

# 8. Открытые вопросы к К-Б

1. **Три числа карточки акта ACC-1** — решение владельца (§ 5.13).
2. **Цена агента 1 копейка — где и кем списывается.** В коде этого нет. В К-Б только строка показа (§ 5.6).
3. **Уровни подписи K6/K7/K8 канвы ↔ `SignatureLevel` ядра** (`simple` | `qualified` | `gov_id`): нужна таблица соответствия.
4. **Подпись INTENT в своём агенте (М2).** В коде подпись мандата — у банка (РП36). Кто подписывает поручение своего агента без банка, ни в ПАО, ни в ядре не описано.

# 9. Карточка решения Р-1603 (номер сверить с чатом дня)

- **Развилка:** форма контракта между экранами и базой.
- **Решение и довод:** шаги пути, а не CRUD по базе. Четыре правила: хэш показанного, идемпотентность, экран ничего не считает, поток — только сигнал. Три поправки к передаче по коду (§ 2). Пять добавленных методов (§ 5.3, § 5.11, § 5.12, § 5.14 POST, § 5.16). Довод: экран — недоверенная среда, подпись мандата у банка, правила (ст. 19, остаток, порог) живут в одном месте — у сервера и Платформы.
- **Отклонено:** экраны прямо на ПАО — ключ агента и ключ УЦ в браузере жить не могут. CRUD по сущностям — логика шагов уехала бы в экран (правило 3). `intent/sign` как подпись ключом агента — противоречит РП36.
- **Кто и когда:** рекомендация чата 18.11. Ждёт «да» владельца.
- **Пересмотр:** выпуск ПАО 1.5.0 (ослабление правила 4). Решение о подписи поручения в М2 (§ 8 п. 4). Договор с банком о токене ИН-ВМ.
- **Где записать:** DECISIONS приложения (`/decision` в КТ-0), реестр развилок, этот документ в `docs/` приложения окном А.
