### С-01. Агент просит новое полномочие — банк сразу показывает его клиенту

| Поле | |
| --- | --- |
| **Ситуация** | Агент клиента просит новое полномочие — например, «покупать продукты до 5 000 ₽ в месяц». Оно вступит в силу, только когда банк клиента его подпишет, а клиент согласится. |
| **Кто участвует** | агент, Платформа, банк, клиент |
| **Что делает система** | Платформа сразу присылает банку уведомление «у клиента новый мандат ждёт подписи». Банк показывает запрос клиенту. Для сверки (например, после перезапуска) банк может перечитать список ждущих подписи. |
| **Какие были варианты** | Только список ждущих — банк сам периодически спрашивает Платформу: клиент видит запрос с задержкой, а тысячи впустую опросов нагружают систему. |
| **Что видит человек** | Запрос «ваш агент просит полномочие — подписать или отклонить» появляется в приложении банка сразу. |
| **Ссылки** | РП74 п. 5 (В1), Р-1172; код — перед пилотом |
| **Тип риска · этап** | доступность · полномочие |

### С-02. Клиент нажал «Подтвердить» два раза подряд

| Поле | |
| --- | --- |
| **Ситуация** | Клиент подтверждает покупку на экране банка и от нетерпения жмёт кнопку дважды. |
| **Кто участвует** | клиент, банк, Платформа |
| **Что делает система** | Если второе нажатие пришло в ту же секунду — это та же запись банка, Платформа отвечает «уже принято» и ничего не повторяет. Если позже — «запрос уже не ждёт решения». Второй записи и второго события нет. |
| **Какие были варианты** | Принимать каждое нажатие как новое решение — риск двойной обработки. |
| **Что видит человек** | Клиент видит одно подтверждение; покупка проходит один раз. |
| **Ссылки** | РП36 «Нюанс UI-К2 ч. 2» п. 4, ПС11 |
| **Тип риска · этап** | деньги · подтверждение |

### С-03. Пока клиент смотрел на экран, сумма покупки изменилась

| Поле | |
| --- | --- |
| **Ситуация** | Клиент открыл запрос подтверждения на 1 500 ₽, отвлёкся, а за это время продавец пересчитал заказ на 1 700 ₽. Клиент нажимает «Подтвердить». |
| **Кто участвует** | клиент, банк, Платформа, продавец |
| **Что делает система** | Вместе с нажатием уходит отпечаток именно того итога, который клиент видел. Платформа сверяет его с текущим; не совпал — подтверждение не принимается. |
| **Какие были варианты** | Пересчитывать отпечаток в момент нажатия — клиент подтвердил бы сумму, которой не видел. |
| **Что видит человек** | Экран говорит: «данные покупки изменились» — клиент видит новую сумму и решает заново. |
| **Ссылки** | totals_hash, инвариант 7, Р-1153 |
| **Тип риска · этап** | деньги · подтверждение |

| **Что видит человек** | «Пока агент приостановлен, подтверждение не приведёт к оплате». |

### С-05. Агент дробит покупку на части, чтобы не просить подтверждения

| Поле | |
| --- | --- |
| **Ситуация** | Клиент разрешил агенту покупать без подтверждения до 3 000 ₽. Агент собирает корзину на 3 450 ₽ и пытается провести её двумя частями — 1 890 ₽ и 1 560 ₽, каждая ниже порога. |
| **Кто участвует** | агент, Платформа, банк, клиент |
| **Что делает система** | Платформа видит, что под одним полномочием за короткое окно прошли две покупки, которые вместе выше порога. Первая часть проходит, на вторую Платформа требует подтверждения человека. Честный агент сам отказывается делить покупку ещё до оплаты. |
| **Какие были варианты** | Отклонять обе части — первая уже одобрена банком, задним числом её не отменить (решение принимается сразу, РП44). Не замечать дробление — порог подтверждения терял бы смысл. |
| **Что видит человек** | Клиент получает в приложении банка запрос подтвердить вторую часть. Если откажет — второй покупки не будет. |
| **Ссылки** | П13, РП44, Р-1133, Р-1152; ПАО 1.5.0 — признак дробления агенту |
| **Тип риска · этап** | деньги · оплата |

### С-06. Связь с продавцом оборвалась в момент оплаты, а банк просит подтверждения

| Поле | |
| --- | --- |
| **Ситуация** | Агент оплачивает заказ, банк отвечает «нужно подтверждение человека», и в этот момент рвётся связь с магазином. Агент не знает, чем кончилась оплата. |
| **Кто участвует** | агент, продавец, банк, клиент |
| **Что делает система** | Агент сначала выясняет исход — по операции, по реквизиту, по заказу — и всё это время держит запрос подтверждения от Платформы, не выбрасывает его по сроку. Когда выясняет, доводит покупку до подтверждения в приложении банка. |
| **Какие были варианты** | Поднять срок хранения запроса выше суммы всех ожиданий — хрупко: держится на сумме параметров и ломается при их правке. |
| **Что видит человек** | Клиент получает обычный запрос подтверждения, как будто обрыва не было. Если подтвердит — покупка завершится. |
| **Ссылки** | Р69 доп. 3, Р-1132, Р-1135; AG-13 |
| **Тип риска · этап** | доступность · оплата |

### С-09. Каталог ключей агентов недоступен

### С-11. Банк стоит за своим прокси — все клиенты делят один лимит

| Поле | |
| --- | --- |
| **Ситуация** | Банк ставит экран мандатов за свой прокси-сервер. Для модуля все клиенты приходят с одного адреса — адреса прокси. |
| **Кто участвует** | банк, клиент |
| **Что делает система** | Сейчас модуль считает лимит частоты по адресу и прокси не доверяет — все клиенты попадают в один счётчик. В инструкции встраивания сказано: лимит по клиенту — на прокси банка, у модуля — с запасом на весь поток. |
| **Какие были варианты** | Решение до пилота: параметр доверенных прокси у модуля — тогда лимит снова по клиенту. |
| **Что видит человек** | Без настройки — при наплыве клиентов экран может отвечать «слишком много запросов» всем сразу. |
| **Ссылки** | К3.3, trustProxy, Р-1175 — перед пилотом |

### С-12. Оператор УПК пытается прочитать чужой запрос подтверждения

| Поле | |
| --- | --- |
| **Ситуация** | Оператор пункта подтверждения (УПК) видит запросы, которые пришли на его страницу. Он пробует подставить в ссылку другой номер запроса. |
| **Кто участвует** | оператор УПК, Платформа |
| **Что делает система** | УПК читает только запросы, направленные на его страницу; чужой — «не найдено», как несуществующий. Случайный, неподбираемый номер — дополнительная мера, а не замена проверки. |
| **Какие были варианты** | Пускать по одному номеру — подобрав номер, оператор прочитал бы чужие покупки. |
| **Что видит человек** | Оператор видит только свои запросы. |
| **Ссылки** | РП74 п. 7, Р-1174; поле привязки — в задаче с кодом |

### С-13. Запрос пришёл с телом не в UTF-8

| Поле | |
| --- | --- |
| **Ситуация** | Агент (или кто-то от его имени) присылает подписанный запрос, тело которого — не текст в UTF-8: сломанная кодировка или нарочно испорченные байты. |
| **Кто участвует** | агент, продавец, Платформа |
| **Что делает система** | Подпись проверяется по самим байтам тела, как они пришли. Если подпись верна, но тело не разбирается как текст — честный отказ «запрос неверен», а не «подпись неверна». |
| **Какие были варианты** | Проверять подпись по тексту — недопустимые байты молча заменяются, подпись перестаёт сходиться, и вместо понятной причины получается ложный «отказ подписи», который ищут не там. |
| **Что видит человек** | Человек ничего не видит; оператор агента получает точную причину отказа и не ищет проблему в ключах. |
| **Ссылки** | К22, #40, Р-1146; ядро v0.12.0 |
| **Тип риска · этап** | данные · любой запрос |
